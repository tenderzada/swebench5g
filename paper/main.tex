\begin{abstract}
Existing benchmarks for AI coding agents---such as SWE-Bench, SWE-Bench Mobile, and BeyondSWE---have primarily targeted general-purpose software in Python, Swift, or cross-repository settings. However, none address the \emph{telecommunications domain}, where software correctness is governed by formal protocol specifications (3GPP), systems are inherently distributed, and bugs often manifest through complex protocol state machine interactions. We introduce \textbf{SWE-Bench 5G}, a benchmark that evaluates coding agents on real bug-fixing tasks drawn from \textbf{free5GC}, the most widely adopted open-source 5G core network implementation. Each task instance is packaged as a self-contained Docker image with a pre-installed Go toolchain, the source code at the buggy commit, existing regression tests, and fail-to-pass tests that verify the fix. Our benchmark introduces three challenges absent from prior work: (1) \emph{specification-driven reasoning}, where agents must interpret 3GPP technical specifications to understand expected behavior; (2) \emph{distributed network function coordination}, where bugs span multiple interacting microservices; and (3) \emph{protocol state machine complexity}, where fixes require understanding stateful signaling procedures. We report baseline results from multiple frontier coding agents on an initial set of task instances and discuss the roadmap toward a comprehensive 5G software engineering benchmark.
\end{abstract}

\section{Introduction}

The rapid advancement of large language models (LLMs) has given rise to a new generation of \emph{AI coding agents}---systems that autonomously navigate codebases, diagnose bugs, and produce patches \citep{jimenez2024swebench}. Benchmarks such as SWE-Bench \citep{jimenez2024swebench}, SWE-Bench Mobile \citep{yao2025swebenchmobile}, and BeyondSWE \citep{shi2025beyondswe} have been instrumental in measuring progress. Yet these benchmarks share a critical blind spot: they evaluate agents exclusively on general-purpose software, leaving open the question of whether coding agents can operate effectively in \emph{vertical, specification-driven domains}.

The 5G telecommunications sector presents a compelling test case. The 5G core network (5GC) is specified by the 3rd Generation Partnership Project (3GPP) across hundreds of Technical Specifications (TS), each defining protocol messages, state machines, and service-based interfaces with precise semantics. Implementations such as free5GC\footnote{\url{https://github.com/free5gc/free5gc}} translate these specifications into production-grade Go code, decomposed into multiple Network Functions (NFs)---AMF, SMF, PCF, UPF, and others---that communicate via HTTP/2 and PFCP protocols. Bugs in this domain are qualitatively different from those in typical open-source projects:

\begin{itemize}
    \item \textbf{Specification-driven correctness.} A ``correct'' fix is not merely one that passes tests, but one that conforms to the relevant 3GPP TS clauses. Agents must locate, interpret, and apply normative protocol text.
    \item \textbf{Distributed microservice architecture.} Network Functions run as independent processes. A single user operation (e.g., UE registration) triggers a signaling cascade across AMF, AUSF, UDM, SMF, and UPF. Bugs may require understanding cross-NF interactions.
    \item \textbf{Protocol state machine complexity.} 5G procedures (registration, session establishment, handover) are defined as multi-step state machines with specific message sequences, timer constraints, and error handling paths.
\end{itemize}

We present \textbf{SWE-Bench 5G}, the first benchmark targeting AI coding agents in the telecommunications domain. Following the BeyondSWE methodology of providing fully reproducible Docker environments, each task instance packages a complete Go development environment with the free5GC source code checked out at the buggy commit, along with fail-to-pass tests that validate the fix. Our contributions are:

\begin{enumerate}
    \item A benchmark framework that maps 5G core network bugs to the SWE-Bench task format, enriched with 3GPP specification references and protocol context.
    \item A three-layer test architecture (unit, protocol compliance, integration) tailored to the distributed, specification-driven nature of 5G software.
    \item An initial dataset of validated task instances drawn from real free5GC issues, with a systematic pipeline for expansion across the full free5GC ecosystem of 20+ repositories.
    \item Baseline evaluation results demonstrating the challenges that 5G domain tasks pose to current frontier coding agents.
\end{enumerate}

\section{Related Work}

\subsection{Software Engineering Benchmarks for Coding Agents}

\textbf{SWE-Bench} \citep{jimenez2024swebench} pioneered the evaluation of coding agents on real-world GitHub issues, drawing 2,294 task instances from 12 popular Python repositories. Each instance pairs an issue description with a fail-to-pass test, enabling automated evaluation. Subsequent work has extended this paradigm along several axes.

\textbf{SWE-Bench Mobile} \citep{yao2025swebenchmobile} targets iOS development with multi-modal inputs (PRDs and Figma designs) over a 500K-line Swift/Objective-C codebase, introducing diff-based intent tests that operate without compiling the application. \textbf{BeyondSWE} \citep{shi2025beyondswe} expands the resolution scope to cross-repository reasoning, domain-specific problem solving, and dependency-driven migrations, packaging each of its 500 instances in a Docker image for full reproducibility. \textbf{SWE-bench Multimodal} \citep{yang2024swebenchmm} extends the original SWE-Bench with tasks requiring visual understanding of JavaScript web applications.

Despite this diversity, all existing benchmarks target general-purpose software. None evaluate agents on \emph{protocol-specified, distributed telecommunications systems}---a domain with distinct challenges around specification compliance, signaling procedures, and network function coordination.

\subsection{Open-Source 5G Core Networks}

free5GC \citep{free5gc} is an open-source implementation of the 3GPP Release 15+ 5G core network, written in Go. It implements the full set of control-plane NFs (AMF, SMF, PCF, UDM, UDR, AUSF, NRF, NSSF, N3IWF) and a user-plane function (UPF). With 2.3K GitHub stars and active development, it is the most widely used open-source 5GC for research and prototyping. Other open-source 5G projects include Open5GS (C-based) and OAI-CN5G (C/C++), but free5GC's Go codebase and modular architecture make it most amenable to automated code generation and analysis.

\section{Benchmark Design}

\subsection{Task Formulation}

Following the SWE-Bench paradigm, we define each task instance as a tuple $\mathcal{T} = (\mathcal{I}, \mathcal{O}, \mathcal{E})$:

\begin{itemize}
    \item \textbf{Input} $\mathcal{I}$: A problem statement derived from the original GitHub issue, augmented with references to relevant 3GPP Technical Specification clauses. The agent also has access to the full source code of the affected NF(s) at the buggy commit.
    \item \textbf{Output} $\mathcal{O}$: A unified diff patch that resolves the issue.
    \item \textbf{Evaluation} $\mathcal{E}$: A test suite partitioned into \texttt{PASS\_TO\_PASS} tests (existing tests that must continue passing) and \texttt{FAIL\_TO\_PASS} tests (new tests that fail on the buggy version and must pass after the fix).
\end{itemize}

\subsection{Task Taxonomy}

We categorize tasks along two dimensions: \emph{scope} and \emph{bug type}.

\paragraph{Scope.}
\begin{itemize}
    \item \textbf{SingleNF}: The bug and fix are contained within a single Network Function. Example: a nil pointer dereference in the PCF's policy authorization handler.
    \item \textbf{CrossNF}: The fix requires coordinated changes across multiple NFs. Example: a registration procedure failure involving both AMF and UDM.
    \item \textbf{Protocol}: The bug violates a specific 3GPP protocol requirement. Example: incorrect NAS message encoding that causes interoperability failures.
    \item \textbf{DataPlane}: The bug affects user-plane forwarding in the UPF or PFCP signaling between SMF and UPF.
\end{itemize}

\paragraph{Bug type.} Following established taxonomies, we classify bugs as: \emph{nil pointer / crash}, \emph{logic error}, \emph{missing validation}, \emph{protocol non-compliance}, \emph{concurrency issue}, and \emph{configuration error}.

\subsection{Three-Layer Test Architecture}

Unlike general-purpose software where unit tests suffice, 5G core network validation requires testing at multiple layers of the protocol stack:

\begin{enumerate}
    \item \textbf{Unit tests} (Layer 1): Test individual functions within a single NF. These are standard Go tests that verify message parsing, state transitions, and business logic. Execution time: milliseconds.
    \item \textbf{Protocol compliance tests} (Layer 2): Simulate protocol messages (NGAP, NAS, HTTP/2, PFCP) and verify that the NF responds according to 3GPP specifications. These tests use mock clients to send crafted messages and assert on response content and status codes. Execution time: milliseconds to seconds.
    \item \textbf{Integration tests} (Layer 3): Start multiple NFs and simulate end-to-end procedures (UE registration, PDU session establishment) using tools such as UERANSIM. Execution time: seconds to minutes. These are reserved for \texttt{Hard} difficulty tasks.
\end{enumerate}

For the initial release, we focus on Layer 1 and Layer 2 tests, which can execute within the Docker container without requiring network connectivity or external simulators.

\subsection{Docker Environment Design}

Following BeyondSWE \citep{shi2025beyondswe}, each task instance is packaged as a self-contained Docker image. The image structure is:

\begin{lstlisting}[language=bash, caption={Docker image internal structure}]
/opt/free5gc-pcf/              # NF source at buggy commit
  internal/sbi/processor/      # Bug location
  go.mod, go.sum               # Dependencies (pre-downloaded)
/opt/test-suite/
  existing_test.go             # PASS_TO_PASS tests
  fail_test.go                 # FAIL_TO_PASS tests
  run_tests.sh                 # Test runner script
/opt/task/
  problem_statement.md         # Issue + 3GPP spec references
\end{lstlisting}

The agent workflow within a container is:
\begin{enumerate}
    \item Read the problem statement (\texttt{/opt/task/problem\_statement.md}).
    \item Run existing tests to verify the environment (\texttt{run\_tests.sh existing} $\rightarrow$ PASS).
    \item Run fail-to-pass tests to confirm the bug (\texttt{run\_tests.sh fail} $\rightarrow$ FAIL).
    \item Analyze the code, understand the bug, and apply a fix.
    \item Run all tests to verify the fix (\texttt{run\_tests.sh all} $\rightarrow$ ALL PASS).
\end{enumerate}

\subsection{Dataset Construction Pipeline}

Our pipeline for constructing task instances consists of five stages:

\paragraph{Stage 1: Candidate mining.} We systematically collect closed issues with linked merged pull requests from the free5GC main repository and its 20+ sub-repositories (one per NF). We filter for issues that describe observable bugs with clear reproduction steps.

\paragraph{Stage 2: Quality filtering.} We exclude issues that involve pure refactoring, documentation changes, dependency upgrades, or require external hardware (e.g., physical gNB equipment). We retain issues where the PR modifies source code files and the bug is reproducible from the issue description.

\paragraph{Stage 3: Commit identification.} For each candidate, we identify the \emph{parent commit} (last commit before the fix PR was merged, representing the buggy version) and the \emph{fix commit} (the merge commit of the fix PR).

\paragraph{Stage 4: Test suite construction.} We construct fail-to-pass tests that exercise the specific bug. Since free5GC has limited existing test coverage, most tests are manually authored based on the issue description and 3GPP specification requirements. Existing tests (pass-to-pass) are either drawn from the repository or authored to verify non-regression of surrounding functionality.

\paragraph{Stage 5: Validation.} Each task instance undergoes a three-step automated validation:
\begin{enumerate}
    \item At the parent commit: existing tests PASS, fail-to-pass tests FAIL.
    \item Apply the ground-truth fix: all tests PASS.
    \item Reset to parent commit: fail-to-pass tests FAIL again (confirming the tests are specific to the fix).
\end{enumerate}

Only instances that pass all three validation steps are included in the dataset.

\section{Pilot Case Study}

We present a detailed walkthrough of our pilot task instance to illustrate the benchmark design.

\subsection{Task: PCF PolicyAuthorization Nil Pointer Panic (Issue \#879)}

\paragraph{Bug description.} The PCF's \texttt{POST /npcf-policyauthorization/v1/app-sessions} endpoint crashes with a nil pointer dereference when a valid request sets \texttt{suppFeat="1"} (enabling traffic-routing support per 3GPP TS 29.514) but omits the \texttt{AfRoutReq} field. The function \texttt{provisioningOfTrafficRoutingInfo()} unconditionally dereferences the \texttt{routeReq} parameter without nil validation.

\paragraph{3GPP context.} The \texttt{suppFeat} field negotiates optional features between NFs. Bit 1 corresponds to ``InfluenceOnTrafficRouting'' (TS 29.514) and ``Traffic Steering Control'' (TS 29.512). When this feature is negotiated, the PCF should handle the \emph{absence} of routing requirements gracefully---the specification does not mandate that \texttt{AfRoutReq} be present when traffic routing is enabled.

\paragraph{Ground-truth fix.} The fix adds a nil check for \texttt{routeReq} at the entry of \texttt{provisioningOfTrafficRoutingInfo()}, returning a fallback PCC rule lookup when the parameter is nil (4 lines changed in 1 file).

\paragraph{Test design.} We authored 5 test cases:
\begin{itemize}
    \item \textbf{PASS\_TO\_PASS} (2 tests): Verify that the function works correctly with a valid (non-nil) \texttt{routeReq}, and that PCC rule lookup by AppId functions correctly.
    \item \textbf{FAIL\_TO\_PASS} (3 tests): (i) Call with nil \texttt{routeReq}; (ii) call with nil \texttt{routeReq} when an existing PCC rule exists for the app ID; (iii) simulate the exact \texttt{suppFeat=1} scenario from the issue.
\end{itemize}

All tests are placed in the same Go package (\texttt{processor}) to access the unexported function directly, using Go's \texttt{recover()} mechanism to detect panics.

\section{Baseline Experiments}

\subsection{Experimental Setup}

We evaluate the pilot task instance with multiple frontier coding agents to establish baseline performance and identify the challenges unique to 5G tasks.

\paragraph{Agent configurations.} We test the following agent-model combinations:
\begin{itemize}
    \item Claude Code (Claude Opus 4.6)
    \item Cursor Agent (Claude Sonnet 4.6)
    \item OpenAI Codex CLI (GPT-4.1)
\end{itemize}

Each agent is given the problem statement from \texttt{/opt/task/problem\_statement.md} and full access to the source code within the Docker container. Agents are evaluated on whether their generated patch causes all 5 tests to pass.

\paragraph{Evaluation metric.} Following SWE-Bench, we use the binary \emph{resolve rate}: an instance is \emph{resolved} if and only if (1) all \texttt{FAIL\_TO\_PASS} tests pass and (2) all \texttt{PASS\_TO\_PASS} tests continue to pass after applying the agent's patch.

\section{Challenges Unique to 5G Benchmarking}

Our experience constructing SWE-Bench 5G reveals several challenges that distinguish it from existing benchmarks:

\paragraph{Limited test coverage.} Unlike mature Python projects that SWE-Bench draws from, free5GC has minimal existing unit tests. Most NF repositories contain zero \texttt{\_test.go} files. This necessitates manual test authoring for every task instance---a significant bottleneck for scaling the dataset.

\paragraph{Specification interpretation.} 3GPP Technical Specifications are written in a dense, semi-formal style with cross-references spanning multiple documents. Even human developers frequently misinterpret specification requirements, as evidenced by the bugs we catalog. Evaluating whether an agent ``understands'' a specification clause is an open challenge.

\paragraph{Environment complexity.} End-to-end 5G testing requires multiple NFs running concurrently, a MongoDB instance, and potentially a RAN simulator (UERANSIM). While our Docker images encapsulate single-NF testing, scaling to CrossNF and integration tests requires orchestrating multi-container environments.

\paragraph{Domain knowledge scarcity.} Telecommunications is underrepresented in LLM training data relative to web development or data science. We hypothesize that agents will struggle more with 5G-specific tasks not because of code complexity, but because of unfamiliarity with the domain's concepts and conventions.

\section{Discussion and Future Work}

\paragraph{Scaling the dataset.} Our immediate priority is expanding from the pilot to 50+ validated instances. The free5GC ecosystem contains 20+ sub-repositories with a combined 2,000+ commits and hundreds of closed issues, providing ample candidate tasks. We plan to develop semi-automated tools for test generation to reduce the manual authoring bottleneck.

\paragraph{Multi-modal inputs.} Following SWE-Bench Mobile's approach, we plan to augment task instances with 3GPP signaling flow diagrams (extracted from TS 23.502) as visual inputs, testing agents' ability to reason about protocol procedures from both textual and diagrammatic representations.

\paragraph{Cross-NF tasks.} The most challenging and realistic 5G debugging scenarios involve tracing issues across multiple NFs. We plan to introduce multi-container task instances where agents must identify and fix bugs spanning AMF-SMF or SMF-UPF boundaries.

\paragraph{Beyond bug fixing.} Future versions may include feature implementation tasks (e.g., implementing a new 3GPP Release 16 feature) and protocol migration tasks (e.g., upgrading from Release 15 to Release 16 compliance).

\section{Conclusion}

We have presented SWE-Bench 5G, the first benchmark for evaluating AI coding agents on telecommunications software engineering tasks. By targeting the free5GC open-source 5G core network, our benchmark introduces challenges around specification-driven reasoning, distributed network function coordination, and protocol state machine complexity that are absent from existing benchmarks. Our Docker-based evaluation framework ensures full reproducibility, and our three-layer test architecture captures the multi-faceted nature of 5G software validation. The initial pilot release demonstrates the viability of this approach, and we outline a clear path toward a comprehensive benchmark covering the full spectrum of 5G core network engineering challenges.

The dataset is publicly available at \url{https://huggingface.co/datasets/tenderzada/SWEBench5G}, and the benchmark infrastructure is open-sourced at \url{https://github.com/tenderzada/swebench5g}.
