# SWE-Bench 5G — 项目介绍（面试用）

---

## 30 秒版本

> 我构建了 **SWE-Bench 5G**，首个面向 5G 核心网的 AI 编程 Agent 评测基准。从开源项目 free5GC 的 16 个仓库中挖掘了 280 个真实 bug，筛选并验证了 10 个任务实例，覆盖 7 个网络功能。每个 bug 打包为 Docker 镜像，配合自动化测试。受 SWE-Skills-Bench 启发，我设计了 **Specification-as-Skill A/B 实验框架**，研究 3GPP 协议规范注入能否提升 Agent 的修复成功率。初步评测发现 Qwen3.5-Flash 能 100% 定位 bug 但 resolve rate 为 0%，揭示了 **Agent 能力而非模型智能是瓶颈**。

---

## 2 分钟版本

### 问题背景

现有的 AI 编程评测基准（SWE-Bench、BeyondSWE 等）全部针对通用软件，没有覆盖**电信领域**。5G 核心网软件有三个独特挑战：代码正确性由 3GPP 协议规范定义、系统是分布式微服务架构、涉及复杂的协议状态机。

### 我做了什么

**1. 构建了数据集和基础设施**
- 编写自动化脚本扫描 free5GC 的 16 个子仓库，挖掘出 280 个候选 bug
- 筛选、编写测试、构建 Docker 镜像、三步自动化验证
- 最终 10 个实例通过验证，覆盖 AMF/PCF/SMF/UDM/NRF/NSSF/AUSF 七个网络功能
- 发布到 HuggingFace，开源全部代码和工具链

**2. 提出了 Specification-as-Skill 研究问题**
- 受 SWE-Skills-Bench（发现 80% 技能注入无效）启发
- 为每个实例编写了 3GPP 规范摘录作为"技能文档"
- 实现了 A/B 实验框架：对比有/无规范注入时的 resolve rate 差异
- 提出三个可验证的假设

**3. 完成了初步评测并发现关键 insight**
- Qwen3.5-Flash 在每次尝试中都正确定位了 bug（提出与官方 PR 完全相同的修复方案）
- 但 resolve rate = 0%——无法在单轮 API 模式下精确编辑代码文件
- **结论：Agent 能力（迭代读写文件）而非模型智能是瓶颈**

### 技术亮点

- **双测试策略**：直接函数调用（可简单调用的函数）+ diff-based intent test（复杂依赖的函数，灵感来自 SWE-Bench Mobile）
- **完整工具链**：挖掘 → 构建 → 验证 → 评测 → 报告，全流程自动化
- **Docker 可复现**：参照 BeyondSWE 方法论，每个 bug 一个隔离环境

## 技术深度问答准备

### Q: 为什么选 free5GC 而不是 Open5GS？

free5GC 用 Go 编写（适合 LLM 生成），模块化架构（每个 NF 独立仓库，便于隔离测试），社区活跃（2.3K stars），且有较多的 bug 修复历史可供挖掘。Open5GS 用 C 编写，代码生成和自动化测试难度更大。

### Q: diff-based intent test 是什么？为什么需要它？

很多 5G 网络功能的核心函数依赖 SCTP 连接、MongoDB、多 NF 协同等运行时上下文，无法在单元测试中直接调用。diff-based intent test 不执行函数，而是**检查源代码中是否存在修复模式**（如 `strings.Contains(src, "GNbId != nil")`）。这借鉴了 SWE-Bench Mobile 的结构化补丁检查思路。

### Q: Qwen 为什么能定位 bug 但无法修复？

Qwen3.5-Flash 在单轮 API 调用中收到完整源码和问题描述，每次都正确诊断出 nil pointer dereference 并提出加 nil check 的修复。但它无法：
1. 精确匹配原文件的代码文本（函数签名记忆偏差）
2. 控制输出格式（每次格式不同）
3. 验证自己的修改是否正确

这些正是 Agent 工具（文件读写、终端执行、迭代修正）解决的问题。

### Q: A/B 实验的预期结论是什么？

我们假设：
- **简单 nil check 类 bug**：规范注入无帮助（修复是通用的防御性编程，不需要协议知识）
- **协议语义类 bug**：规范注入有帮助（例如需要知道某个字段是 OPTIONAL）
- 这种**差异化结论本身**就是论文贡献，因为它指导了 5G Agent 的设计——应该内置规范检索还是其他能力

### Q: 与 SWE-Bench 的核心区别？

| 维度 | SWE-Bench | SWE-Bench 5G |
|------|-----------|--------------|
| 领域 | 通用 Python | 5G 电信（Go） |
| 正确性标准 | 测试通过 | 测试通过 + 协议合规 |
| 独特挑战 | 代码理解 | 规范理解 + 分布式系统 |
| 新研究维度 | 无 | Specification-as-Skill |
| 测试方法 | 运行时测试 | 运行时 + diff-based intent |

### Q: 项目规模和工作量？

| 指标 | 数值 |
|------|------|
| 代码量 | ~3000 行（Python 脚本 + Go 测试 + Shell 工具） |
| 实例数 | 10 已验证 + 11 待验证 + 280 候选 |
| 文件数 | ~100 个文件（含规范摘录、实例配置、模板） |
| 覆盖 NF | 7/8 个核心网络功能 |
| 论文 | NeurIPS D&B Track 格式，含 baseline 数据 |

## 展示话术建议

### 开场

"我最近在做的一个项目叫 SWE-Bench 5G。大家可能听过 SWE-Bench——评测 AI 写代码能力的基准测试。我把这个思路带到了 5G 核心网领域，因为电信软件有一个独特的特点：代码的正确性不是由开发者定义的，而是由 3GPP 协议规范定义的。"

### 过渡到研究问题

"在做的过程中，我发现一篇 SWE-Skills-Bench 的论文说 80% 的技能注入对 Agent 没用。这让我想到一个问题：如果我把 3GPP 规范也作为一种'技能'注入给 Agent，它到底有没有用？于是我设计了一个 A/B 实验框架来回答这个问题。"

### 收尾亮点

"最有意思的发现是：Qwen 在每次尝试中都能正确诊断出 bug——它知道需要加一个 nil check。但它就是写不出能正确应用到代码里的补丁。这说明在真实的软件工程场景下，**模型的理解能力已经够了，瓶颈在 Agent 的工程能力**——能不能精确地读文件、改文件、验证结果。"
